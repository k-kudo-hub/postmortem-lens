# postmortem-lens: 障害のストックでリポジトリを検査する

重要なのは、利用者が、自身が公開しているサービスの弱い箇所と、その重要性に気づけることである。
重要な障害は多く、報告を読みきれない。観点を持たずにコードを読んでも、同じ起き方をする箇所は拾えない。
このスキルは、直近の大規模障害から取り出した弱い箇所（観点）を持ち込み、いま開いているリポジトリに同じものがないかを探す。

## 守ること

- 読むだけにする。ファイルを書き換えない。リポジトリの中身を Web（WebFetch・WebSearch・外部の API）に送らない。コマンドは、ファイルの一覧を見る `git ls-files` だけを使う
- 「当てはまる」と書くのは、リポジトリの中で実際に読んだファイルと行を根拠に示せるときだけにする。推測で当てはめない
- 「当てはまる」の根拠と重要度の理由には、ストックのどれかの弱い箇所と同じ仕組みのものだけを使う。ストックのどの弱い箇所にも当たらない弱さ（例: データの保存先が消えやすい）は、重要度の理由に混ぜず、最後の「ストックの外で気づいたこと」に分けて書く
- 「同じ起き方をした障害」には、根拠で示した仕組みが、その障害の弱い箇所の `whatHappened` と同じものだけを並べる。障害の仕組みがリポジトリにない（例: 再送の設定がないのに、再送が負荷を押し上げた障害を挙げる）なら、その障害は挙げない
- 障害の引用は、ストックの `quotes` と `reportedFixes` をそのまま写す。言い換えない
- ライブラリの既知の脆弱性（CVE）の検出は対象にしない。それは Dependabot のような脆弱性スキャナーの領分である

## 手順

### 1. ストックを読む

障害のストックは `${CLAUDE_PLUGIN_ROOT}/stock/` にある。Glob でこのディレクトリの `*.json` をすべて探し、1つずつ Read で読む。
1つのファイルが1つの障害で、`weaknesses` の各項目が、その障害を起こした弱い箇所である。各項目の中身は次のとおり。

| フィールド | 中身 |
|------------|------|
| `whatHappened` | その障害で、この弱い箇所が何を起こしたか（仕組みが同じかを比べる基準） |
| `quotes` | 一次報告の本文の抜き出し |
| `reportedFixes` | 報告が挙げた対策（一次報告の本文の抜き出し。ないこともある） |
| `lookFor` | リポジトリで探すものの手がかり |
| `countermeasures` | postmortem-lens が、利用者のリポジトリで今とれる形に一般化した対策 |

### 2. リポジトリを知る

いま開いているリポジトリ（作業ディレクトリ）が何かを、次の順に確かめる。

1. README と、パッケージの定義（`package.json`・`go.mod`・`pyproject.toml`・`Cargo.toml`・`pom.xml`）から、何のサービス・ライブラリか
2. インフラの定義があるか: Kubernetes のマニフェスト・Helm のチャート・Terraform・docker-compose・CI/CD のワークフロー
3. 入口と依存先: HTTP サーバー・ヘルスチェックの処理・データベースやキャッシュへの接続・外部 API の呼び出し・定期実行のジョブ・キューのワーカー

リポジトリが大きいときは、Grep で `lookFor` に出てくる語（`livenessProbe`・`retry`・`timeout`・`maxSurge`・`health`）から当たりを付ける。

### 3. 弱い箇所ごとに判定する

ストックのすべての弱い箇所について、次の4つのどれかに決める。

| 判定 | 決め方 |
|------|--------|
| 当てはまる | 同じ仕組みの弱い箇所が、リポジトリの中にある。根拠のファイルと行を示せる |
| 対策済み | 同じ仕組みの箇所はあるが、対策が入っている（例: 再送が指数バックオフになっている）。根拠のファイルと行を示せる |
| 当てはまらない | このリポジトリには、その弱い箇所が生まれる作りがない（例: キューがないので、溜まった処理の消化の弱さは生まれない） |
| 判断できない | 関係する部分がこのリポジトリの外にあり、確かめられない（例: インフラが別のリポジトリで管理されている） |

別々の障害の弱い箇所が、リポジトリの同じ箇所を指すときは、1つの「弱い箇所」にまとめ、同じ起き方をした障害を並べる。

### 4. 重要度を決める

「当てはまる」と決めた弱い箇所ごとに、次の2つの軸で重要度を決める。理由は、このリポジトリの構成に即して書き、その弱い箇所（ストックと同じ仕組み）が起こすことだけを根拠にする。

**影響の広さ**

- A: サービス全体が止まる、またはデータが失われる
- B: 一部の機能、または一部の利用者が使えなくなる
- C: 遅くなる、または一時的なエラーで済む

ライブラリ・ツールの OSS では、そのライブラリを使う利用者のサービスに何が起きるかで決める。

**条件のそろいやすさ**

- 1: 平常運用で起きる（デプロイ・再起動・ピークの時間帯・フェイルオーバー・ノードの保守）
- 2: よくある不調が1つ重なると起きる（依存先の遅れ・一部の容量の欠け・ネットワークの不調）
- 3: 複数の不調が重なったときだけ起きる

| | 1 | 2 | 3 |
|---|---|---|---|
| A | 高 | 高 | 中 |
| B | 高 | 中 | 低 |
| C | 中 | 低 | 低 |

### 5. 結果を出す

次の形の Markdown で、会話に出す。弱い箇所は重要度の高い順に並べ、同じ重要度の中では影響の広さが大きい順にする。

```markdown
# postmortem-lens の検査結果: {リポジトリ名}

- 検査したもの: {何のサービス・ライブラリか、1文}
- 照らしたストック: {障害の件数}件の障害・{弱い箇所の件数}個の弱い箇所（{最も古い発生日}〜{最も新しい発生日}）
- 結果: 当てはまる {件数}・対策済み {件数}・当てはまらない {件数}・判断できない {件数}

## 弱い箇所（重要な順）

### 1. 【{高|中|低}】{弱い箇所の名前。このリポジトリでの言い方にする}

- 重要度の理由: 影響の広さ {A|B|C}（{理由}）／条件のそろいやすさ {1|2|3}（{理由}）
- 根拠:
  - `{ファイルのパス}:{行}` — {何がどう弱いか}

    ```{言語}
    {根拠の行の抜き出し}
    ```
- 同じ起き方をした障害:
  - [{障害の title}]({source.url})（{startedAt}、{provider}）: {whatHappened}
    > {quotes から1つ、そのまま}

    報告が挙げた対策（reportedFixes から1つ、そのまま。なければ書かない）:
    > {reportedFixes の文}
- 今とれる対策:
  - {countermeasures の action を、このリポジトリに即して具体的にしたもの}（最初の一歩: {firstStep を、このリポジトリのファイル名で具体的にしたもの}）

## 対策済みだった箇所

- {弱い箇所の名前}: `{ファイルのパス}:{行}` — {入っている対策}

## 当てはまらなかった弱い箇所

- {弱い箇所の名前}（{障害の title}）: {このリポジトリにその作りがない理由}

## このリポジトリでは判断できなかった弱い箇所

- {弱い箇所の名前}（{障害の title}）: {確かめられなかった理由}

## ストックの外で気づいたこと

- {ストックのどの弱い箇所にも当たらないが、読んでいて気づいた弱さ。`{ファイルのパス}:{行}` を添える。なければこの見出しごと書かない}
```

当てはまる弱い箇所が1つもないときは、「弱い箇所（重要な順）」に「ストックの障害と同じ起き方をする箇所は見つかりませんでした」と書き、残りの見出しはそのまま出す。

最後に1行で、結果をファイルに保存したいときは頼めばよいことを伝える。
